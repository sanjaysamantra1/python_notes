REST ARCHITECTURE
-----------------
-REST = Representational State Transfer
-Stateless communication: The server does not remember any information about previous requests.
-Each request contains all required information: Since REST is stateless, every request must contain all data needed for processing
-Resource-based URLs: Resources are identified using URLs

Examples:

POST     /users
PUT      /users/1   
PATCH    /users/1

-HTTP is a Protocol, HTTP provides the rules for client-server communication

	Request structure
	Response structure
	HTTP methods
	Headers
	Status codes
	Request body
	Response body
	Caching behavior
	Authentication mechanisms
	Content types



HTTP Methods
============
GET -Fetch Data from the server (ex: search products)
      Doesn't change Data
	  Safe, Idempotent, No Request Body
	  
POST -Send Data to create a new resource( sign up )
	   while fetching the Data if client wants to send parameters in Request body not in Request URL
	   Not Idempotent, Request Body

PUT -Replace an existing resource completely
      Idempotent, Full Update , Complete Object in Request Body
	    
PATCH -Update only specific fields of a resource
		update password/mobile 
		Idempotent, Partial Update , More Efficient than PUT, Request Body

DELETE -remove a resource/delete a record from DataBase
		 Delete an account
		 Idempotent, No Body
		 
HEAD -Get Headers only	, Same as GET but no response body
       Used For Checking existance, performance checks
	   
OPTIONS -Returns Supported HTTP Methods
          Used in CORS
          Browser preflight requests		  
		 




Idempotent
----------
-An HTTP method is idempotent if making the same request multiple times results in the same server state.
-The response may be same or different, but the data on the server doesnt change after the first request.
-POST is non-idempotent, Whereas GET,PUT,PATCH,DELETE are idempotent

POST   api/users
{'name':'sanjay','address':'Bangalore'}
1st request --> User Created ( id=10 )
2nd request --> User Created ( id=11 )
3rd request --> another User Created ( id=12 )
-Database state changes every time, POST is non-idempotent


PUT  api/users/1 
{'name':'sanjay','address':'Bangalore'}
1st request --> user becomes  (Sanjay,Bangalore)
2nd request --> user is still  (Sanjay,Bangalore)
10th request --> user is still  (Sanjay,Bangalore)
-DataBase state stays the same, PUT is idempotent



PUT vs POST
-----------
-PUT for UPDATE operations, POST for CREATE operations.
-PUT is idempotent, where POST is non-idempotent.
-Use PUT when you want to modify a singular resource which is already a part of resources collection.
-Use POST when you want to add a child resource under resources collection.


PUT vs PATCH
------------
-PUT is used to replace a complete resource.
-PATCH is used to apply partial modifications to a resource.

Path Parameters
===============
-A path parameter is a variable value embedded directly into the URL path.
-Used to pass values through URL. defined using {}
-FastAPI supports Path Parameter with Type Hint, when not followed FastAPI automatically returns a validation error.

@app.get("/users/{user_id}")
def get_user(user_id:int):  #user_id must be an integer
    return {
        "user_id": user_id
    }

Request: http://localhost:8000/users/101


Multiple Path Parameters:
@app.get("/users/{user_id}/orders/{order_id}")
def get_order(user_id: int, order_id: int):
    return {
        "user_id": user_id,
        "order_id": order_id
    }

-Optional Query Parameters: Use a default value

Headers
=======
-Headers contain metadata about the HTTP request.

Request headers: The headers sent from Client to Server
Response headers: The headers sent from Server to Client


from fastapi import FastAPI, Header, Response
app = FastAPI()
@app.get("/hello")
async def hello(
    response: Response,
    authorization: str | None = Header(default=None),
    x_request_id: str | None = Header(default=None),
):
    # Request headers received from the client
    print("Authorization:", authorization)
    print("X-Request-ID:", x_request_id)

    # Response headers sent back to the client
    response.headers["X-Response-ID"] = "response-123"
    response.headers["X-Custom-Header"] = "hello"

    return {
        "message": "Hello",
        "received_headers": {
            "authorization": authorization,
            "x_request_id": x_request_id,
        },
    }

Dependency Injection
====================
-A dependency is reusable logic that a route needs, and FastAPI automatically executes and provides its result.

Benefits:
	-Reusable Code
	-Clean Architecture
	-Loose Coupling

Example:
from fastapi import Depends

def get_current_user():
    return {"id": 101, "name": "Sanjay", "role": "admin"}

@app.get("/products")
def get_products(user=Depends(get_current_user)):
    return {"message": f"Products requested by {user['name']}", "user": user}







Middleware
==========
-Common logic that runs around every request
Client --> Middleware --> Route --> Response 

async def log_request(request: Request, call_next):
	execute middleware logic
	call_next



Logging
Request timing
CORS
Adding response headers
Global request/response processing


Dependency = logic needed by a particular route. 
			 ex: several APIs need the current user.
Middleware = logic that runs around every request.
			 ex: you want to log every request.


|                              | Dependency Injection            | Middleware                 |	
| -----------------------------| --------------------------------| ---------------------------|
| Scope                        | Selected routes                 | All requests               |
| Purpose                      | Provide reusable logic/data     | Process request/response   |
| Runs                         | When route declares `Depends()` | Automatically              |
| Can access route parameters? | Yes, through dependencies       | Not directly               |
| Can return data to route?    | Yes                             | No, not as dependency data |
| Typical use                  | Auth, DB session                | Logging, CORS              |
| Position                     | Before route execution          | Around route execution     |

CORS
====
CORS = Cross-Origin Resource Sharing

-It is a browser security mechanism that controls whether JavaScript running on one origin is allowed to access resources from another origin.
-CORS Does Not Mean "Backend Blocks Requests". CORS is primarily a browser-enforced security mechanism.
-The browser has a security concept called the:Same-Origin Policy , It restricts JavaScript from freely interacting with resources belonging to another origin.

-An origin consists of: Protocol + Host + Port
-Changing any one of these can make it a different origin.
-CORS decides which origins can access the API from a browser; CORSMiddleware enforces that policy in FastAPI.




ex:
from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)

Async FastAPI
=============
-Synchronous vs asynchronous execution
-Blocking vs non-blocking operations
-I/O-bound vs CPU-bound tasks
-Concurrency vs parallelism
-Why async is useful for APIs
-Event loop concept




-FastAPI Supports asyncio , so our API can handle multiple waiting tasks efficiently.
-Databse calls, Http Requests , File I/O
-Use asyncio.gather() to run Multiple Async Operations Concurrently
 user, order = await asyncio.gather(get_user(), get_orders())
-async def automatically doesn't make everything faster. The benefit comes when the endpoint performs non-blocking I/O.
-


def endpoint : Regular Synchronous Code
async def endpoints : asynchronous code; it can await non-blocking operations
await : pauses only the current request while its I/O is pending, allows the server to work on other requests


CPU-Bound vs I/O-Bound:
I/O Operations: Database,  HTTP API, File Operations, Redis
CPU-Bound : Large calculations , Video processing
